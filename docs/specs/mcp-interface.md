# Specification: mcp-interface

Status: implemented; verification recorded in the task checklist, 2026-11-09.
Manual Bearer API-token setup approved by the user. No MCP OAuth support is
claimed; native OAuth compatibility must be rechecked on upstream upgrades.
Depends on [semantic-contract](semantic-contract.md) and
[resource-efficiency](resource-efficiency.md). Intent: [ADR-010](../decisions/0010-semantic-api-and-mcp.md).

## Objective and architecture

Expose the whole Better UI model to assistants, including smaller models, without
making them reconstruct business rules from raw Vikunja fields. Implement with
`github.com/modelcontextprotocol/go-sdk`, pinned to a verified stable release at
implementation time. Do not treat the SDK's moving main branch as a release.

Required path: Codex or another AI client -> Better UI MCP URL (Streamable HTTP)
-> shared Go services -> configured Vikunja REST API.
The MCP endpoint runs in the existing Go server. No local stdio adapter or
additional client-side process is part of this feature.
The adapter handles transport, typed input/output and caller context. Domain
classification, recurrence, completion and validation remain in `internal/service`.
Do not call GraphQL over loopback or simulate browser cookies/CSRF tokens.

No LLM runs on the server. Reading/classifying data is deterministic. Suggestions
are generated by the client assistant; mutations require a delegated user action.
Tool annotations describe effects, but cannot prove human consent or enforce
client UX. The server independently enforces permissions and business invariants.

## System understanding and discovery

- Publish a compact overview of task kinds, time semantics, recurrence, views,
  recovery and permissions. It must link to every concept family in the inventory.
- Resource namespace: `better-ui://concepts/{concept}`. Resources contain
  static explanations/examples, never another caller's tasks or credentials.
- A read-only `explain_concept` tool exposes the same content for clients that do
  not consume resources. It accepts a documented concept identifier; unknown
  identifiers return the small index rather than invented guidance.
- Tool descriptions state when to use the action, its main constraints and side
  effects. Essential constraints cannot exist only in an optional resource.
- Compile/embed stable descriptions once; do not parse Markdown files per call.
  Keep canonical examples linked/tested to prevent parallel prose from drifting.

## Typed surface

These names are the implemented tool contract. Each family uses
explicit Go types/JSON Schema; never an arbitrary JSON or REST execution escape.

| Tool or family | Input intent | Output/constraint |
| --- | --- | --- |
| explain_concept | Concept or overview | Static model explanation and relevant actions |
| get_context | No task query | Effective timezone, source/readiness and visible project/label context, paged where necessary; no token metadata secrets |
| list_tasks | Existing named scope, filters, order, page | Compact classified tasks, totals/completeness and pagination |
| get_agenda | Local day, filters | Scheduled sessions, finish obligations, projections, optional active work as distinct sections |
| get_recurring_overview | Bounded reporting period, filters | Series, native rule and frequency/projections; no invented stored occurrences |
| get_task | ID, explicit detail sections | Version, dates, kind, recurrence, reminders; relations/attachment metadata only when requested |
| get_activity | Recent activity and optional all-time totals | Authorized aggregates with generation time/completeness; not global public-token data |
| create_one_time_task / create_recurring_task / create_job | Kind-specific typed inputs | Existing confirmed/repair-required creation result |
| update_task | ID, expected version, explicit changes | Verified result; omitted fields preserved by adapter contract |
| complete_task / skip_occurrence | ID and occurrence preconditions | Completion/renewal/history outcome and applicable recovery |
| delete_task | Explicit ID and current precondition | Named deletion outcome; client confirms destructive intent |
| undo_completion / repair_task | Issued capability | Existing scoped, expiring recovery; no arbitrary 'repair anything' |
| set_task_relation / create_subtask | Explicit relation action | Native relation constraints and partial result |
| list_comments / create_comment / update_comment / delete_comment | Task and explicit comment action | Bounded discussion, safe text format and outcome |
| create_label | Explicit name | Ordinary label; never silently rename user labels |

`get_task` detail sections cover attachment metadata and diagnostics. Attachment
binary upload/download remains an explicit first-release limitation until a safe
MCP transport is specified: browser-session media URLs are not usable as bearer
MCP downloads. Document the concept without pretending this operation is supported.
Project administration, avatar editing, arbitrary upstream operations and token
management are not added merely because Vikunja supports them.

Use one output schema per action. Include typed outcome, affected entity/version,
completeness/issues and recovery information as applicable. List items omit large
bodies by default. Return `structuredContent` and a concise compatible text
representation according to the chosen SDK/protocol; measure duplicated bytes.
Errors must be actionable and safe, distinguish missing rights from empty data,
and not promise that an uncertain write failed without side effects.

## Scheduling and editing contract

Reuse existing scope and projection rules. Agenda composition must not replace
Today with Active or call a flexible month window a booked month-long session.
Group optional active work separately and mark partial sections independently.
For actual sessions, compute interval overlaps deterministically; adjacent
end/start instants do not overlap. A shared planning window only means both tasks
are available then. Keep computed conflicts bounded and report truncation.

Update input uses explicit changes: omitted/null preserves; `clear` names
`deadline`, `startAt`, `endAt` or `recurrence`; provided lists replace and `[]`
clears labels/reminders. Conflicting set/clear representations are rejected. This is
an MCP adapter contract, not a change to the existing full-form GraphQL mutation.
Load the current task, check expectedVersion, merge the explicit changes and call
the existing edit service. Do not copy full-form defaults over untouched values.
Absolute time and local-time input forms must be unambiguous; reject conflicting
representations and nonexistent/ambiguous local times using existing rules.

Delegated replanning uses these same actions and preconditions. Show what changed
and what failed. First release need not add a bulk tool: sequential typed edits
are acceptable, with no all-or-nothing claim. Do not automatically shift deadlines,
reminders or the whole recurring series when the user only requests a plan change.

## Authorization and transport decision

Requirement: tokens are created in Vikunja, configured outside model arguments,
never issued/stored/logged by Better UI. Caller credentials must never fall back
to APP_VIKUNJA_API_TOKEN. Upstream URL comes only from trusted configuration.

Evidence reviewed 2026-11-09:

- [Vikunja 2.7 API token model](https://raw.githubusercontent.com/go-vikunja/vikunja/v2.7.0/pkg/models/api_tokens.go)
  stores route permissions, expiry and owner (including bot owner); these do not
  establish an MCP audience-binding mechanism.
- [Vikunja 2.7 MCP settings route](https://raw.githubusercontent.com/go-vikunja/vikunja/v2.7.0/pkg/routes/api/v2/mcp.go)
  explicitly rejects API tokens. Do not use `/mcp/info` as token introspection.
  The settings advertise presets, not permission proof for a supplied credential.
- [Vikunja OAuth documentation](https://vikunja.io/docs/oauth-server/) describes
  custom `vikunja-` redirect schemes and JSON token requests. It is not evidence
  of a plug-and-play standards-compliant remote MCP OAuth flow.
- [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
  separates HTTP authorization from stdio credentials supplied through environment.
  [Security guidance](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
  forbids token passthrough without appropriate issuance/validation.

| Alternative | Fit to user's setup | Tradeoff / acceptance needed |
| --- | --- | --- |
| Remote HTTP with directly supplied Vikunja API token | Closest to native Vikunja setup and hosted Better UI; selected | Custom Bearer profile approved; no MCP OAuth compliance claim |
| Remote HTTP with compliant authorization and separate upstream credentials | Stronger standard client interoperability | Needs proven issuer/delegation support or new infrastructure; may violate simplicity/no-token-store constraints |

The user explicitly excluded local stdio and approved remote Bearer API tokens
on 2026-11-09. The selected mode deliberately follows native Vikunja client setup,
not the MCP OAuth authorization profile. Do not advertise OAuth metadata or add
an issuer/store. Native MCP authorization is checked before handling each request;
every subsequent REST action is checked by Vikunja under that same token.

OAuth check: [official MCP help](https://vikunja.io/help/mcp/) states OAuth is not
supported. Both [v2.7.0 handler](https://raw.githubusercontent.com/go-vikunja/vikunja/v2.7.0/pkg/modules/mcp/mcp.go)
and [main handler](https://raw.githubusercontent.com/go-vikunja/vikunja/main/pkg/modules/mcp/mcp.go)
reject JWTs and require an API token plus mcp:access. General Vikunja OAuth login
is therefore not a supported MCP OAuth route. Verified 2026-11-09 by source and
documentation, not by sending credentials to a production instance.

Support API-token permission configurations, including bot-owned tokens, as far
as verified upstream capabilities allow. Session JWTs/link-share credentials are
not promised without separate testing and an explicit scope decision. No automatic
refresh, password auth or credential probing. Document required permissions per
workflow, including metadata and history/marker writes. Missing rights must fail
safely, not force a recommendation for full access in all cases.

## Isolation, retries and resource lifetime

Caller context must include upstream identity and authorization scope. Existing
Undo/repair grants in `internal/service/capability.go` are session-bound; define
a domain-separated MCP principal binding before exposing them. Prevent cross-token,
cross-user and UI/MCP replay; revalidate current upstream access on recovery.
Never put raw tokens into serialized capabilities or use an MCP session ID as auth.

Share immutable definitions and safe HTTP transports, not credential-bearing
state. Keep in-flight coalescing within the same authorization boundary and do
not create an unbounded token->client map. Bound bodies, output, candidate counts,
concurrency and runtime; honor cancellation throughout upstream calls.

Read operations perform no writes, including implicit repair. Existing mutation
reconciliation remains; do not blindly retry creates/completions. No guarantee of
durable generic idempotency is introduced without storage. Task/comment content
is untrusted data, never server instructions or executable prompts.

## Acceptance and evaluation

- Shared fixtures prove list classification, dates, recurrence, reminder edits,
  relations and recovery agree with existing services/GraphQL.
- Read-only, custom-scope, write-capable, bot, revoked/expired and inaccessible
  project tokens are tested against isolated supported Vikunja. Insufficient
  metadata access is an explicit error, never a successful empty response.
- Two concurrent principals cannot share task results, transport credentials or
  recovery capabilities. Cancellation stops work without credential leakage.
- Client compatibility tests cover discovery, schemas, errors and selected transport.
  Pin SDK version and record tested protocol/client versions before release.
- The user declined model-runtime evaluation on 2026-11-09. Research the design,
  choose the organization independently and run deterministic protocol/semantic
  checks. Record bytes/calls and unsupported client features; do not report
  model accuracy or require the user to validate models.
- Scenarios cover day overview, monthly flexible work, session versus deadline,
  recurring skip/complete, reminders, Revisit, relations, partial results and
  delegated rescheduling. No bespoke per-scenario system prompts. A no-resource
  client must still learn critical constraints from tools and results.
- Any unauthorized mutation is a release blocker. Semantic mistakes require a
  regression fixture and contract correction; model behavior cannot be guaranteed
  universally and must not be advertised as such.

## Structure, style, commands and rollout

`internal/mcp` contains only protocol adapters, schemas and embedded
concept resources; unit tests sit beside them. Cross-boundary tests go under
`tests/integration`. Wire Streamable HTTP into `cmd/server/main.go`; no new local
CLI entrypoint is needed. Keep package/function
documentation, small consumer interfaces, context propagation and current gates.
Use typed handlers rather than `map[string]any` business payloads.

After SDK installation and adapter implementation, run in the matching Dev Container:

```sh
go test -race -count=1 ./internal/mcp/... ./internal/service/... ./tests/integration/...
task validate
task test
task gen:check
```

The task checklist records verification and remaining evidence limits.
Real-token fixtures use isolated demo instances, never production task mutations.
Measure discovery and representative tool workloads under the resource-efficiency
specification. Document exact URL/header setup after authorization is verified.

No database or task migration. Keep MCP optional and existing UI/GraphQL behavior
unchanged. Rollback removes/disables the adapter; native task changes already
requested by users remain. Always preserve permissions and semantics; ask before
new persistence/issuers or changed recurrence rules; never expose arbitrary API
execution, credentials or unverified auth-compliance claims.

## Agent-facing design decision — 2026-11-09

The user's goal is understanding the whole system with little repeated prompting.
This section is our design assessment, not a claim of measured small-model accuracy.

Sources and limits:

- [Anthropic's tool engineering report](https://www.anthropic.com/research/writing-tools-for-agents)
  favors distinct workflow-oriented tools, relevant bounded responses and actionable
  errors over mechanical REST wrappers. It also recommends empirical evaluations;
  the user explicitly declined that part. Its findings do not prove performance
  for every small model.
- [AWS tool-definition guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/mcp-strategies/mcp-tool-strategy-definitions.html)
  recommends explicit purpose, prerequisites, examples, input/output schemas and
  enums for finite choices. Definitions consume context, so clarity must earn its cost.
- [MCP tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
  defines structured results, output schemas and effect annotations. Annotations
  are hints, not authorization. Keep the compatible text representation of results.

Our choice compared with the strongest alternatives:

| Organization | Benefit | Why choose or reject here |
| --- | --- | --- |
| Small set of semantic reads plus explicit mutations | Server resolves classification; actions remain understandable and composable | Selected; combines useful reads without mixing read intent with writes |
| One generic task tool with an action argument | Shorter tools list | Rejected: conditional inputs and mixed effects hide prerequisites and weaken read/write annotations |
| One wrapper for every REST route | Complete native coverage and simple mapping | Rejected: exposes internals and forces models to reconstruct the Better UI rules |
| Large initial system manual | All concepts always available | Rejected: repeats irrelevant detail; use a compact overview and on-demand explanations |

Concrete rules:

1. Initial instructions contain the system distinction and routing: day overview,
   named lists, task detail, concept help. No promise that the client reads resources.
2. Each tool says when to use it, what it returns, essential constraints and the
   next step on incomplete/conflict/repair results. Never depend on a long resource
   for a rule necessary to safely call that tool.
3. Use finite enums for scopes, sort choices and recurrence modes. Use explicit
   `taskId`, local date formats, units and defaults; never make the model invent IDs.
4. Return server-classified sections and readable titles with stable IDs. List
   responses omit descriptions; detail is requested separately. Bounds and missing
   information remain visible. Empty, forbidden and incomplete are different states.
5. Keep static concept resources and `explain_concept` equivalent. Overview names
   available concepts; unknown names return the index. Include short intention →
   action → outcome examples for ambiguous planning and lifecycle decisions.
6. Edits require a freshly read version and change only explicit fields. Recovery
   follows returned capabilities. Never suggest a blind retry after uncertain writes.
7. Reuse immutable definitions and transports. Bound response pages and text;
   compute business classifications in shared services. Measure discovery bytes
   and upstream calls rather than claiming token savings from a shorter name.
8. Regression fixtures check Today versus Active, time windows versus sessions,
   edit preservation, unsupported combinations, annotation/schema completeness,
   denied writes and partial results. They prove server behavior, not model judgment.

## Implemented surface

SDK: `github.com/modelcontextprotocol/go-sdk v1.8.0`. Transport is stateless
Streamable HTTP with JSON responses; POST only, no standalone SSE subscription.
The SDK HTTP client passes initialize, discovery and resource reads. Raw protocol
fixtures cover `2025-11-25`, including original HTTP cancellation. Compatibility
with individual desktop clients and model accuracy remain unverified.

| Tools | Purpose |
| --- | --- |
| `explain_concept`, `get_context` | Rules, effective timezone/source/readiness, paged projects and ordinary labels |
| `list_tasks`, `get_task` | Named views; detail with optional relations and attachment metadata |
| `get_agenda`, `get_recurring_overview`, `get_activity` | Day sections, normalized weekly/monthly/yearly rhythm, caller-only activity |
| `create_one_time_task`, `create_recurring_task`, `create_job` | Separate creation contracts using shared services |
| `update_task`, `delete_task` | Explicit changes or guarded deletion using a current version |
| `complete_task`, `skip_occurrence` | Existing lifecycle; recurrence requires the displayed due instant |
| `undo_completion`, `repair_task` | Returned short-lived caller-bound capabilities |
| `set_task_relation`, `create_subtask`, `create_label` | Existing relation rules, inheritance and ordinary labels |
| `list_comments`, `create_comment`, `update_comment`, `delete_comment` | Native discussion and author permissions |

Permissions are enforced by native routes, not tool discovery. All calls require
`mcp:access`. Calendar reads need user profile and task reads; filtered views also
need accessible projects and relevant label metadata. Context needs project/label
reads. Creation needs task creation, project access and label association rights;
recurring completion additionally needs history creation, live-task update and
marker writes. Relations and comments need their corresponding native permissions.
A missing permission is never substituted with the configured app token. Use the
native read-only/write presets or explicit route permissions matching the workflow.

Limits and defaults:

- 1 MiB request bodies, 30-second request lifetime, 16 simultaneous requests.
  No token/client cache; transports and immutable definitions are shared.
- Task pages default to 30, maximum 100; page range 1–1,000,000. Metadata pages
  and optional sections remain bounded. Detail text is truncated at 8,000 runes;
  label/reminder/relation collections are capped at 100 with truncation flags.
- `PERIOD`, `COMPLETED_JOBS` and `ALL_JOBS` require inclusive local `from`/`through`
  dates. Job bounds select completion dates; `ALL_JOBS` defaults to start ascending.
- Agenda sections independently report completeness/errors. Availability is not
  a reservation; only actual sessions produce overlap pairs (maximum 100).
- `get_context` works without a configured timezone and reports schedulingReady.
  Calendar tools require a valid effective timezone; the bot-only fallback below
  is the sole exception to the profile-only rule.
- Mutations return a compact task reference/version. Use `get_task` for full
  detail. Newly created tasks are re-read so returned versions match native reads.
- Omitted dates survive partial edits as exact instants, including DST folds and
  seconds. Explicit new ambiguous local times remain rejected. Unsupported native
  recurrence can be cleared/replaced; it cannot silently round-trip as another rule.
- Comments preserve native author rights and have no optimistic version guard.
  Task version checks are not an upstream atomic compare-and-swap guarantee.
- Activity exposes recent activity and optional all-time totals, not arbitrary
  analytical filters. Attachments expose metadata, not binary transfer tools.
- No project administration, attachment upload/download, arbitrary REST execution,
  bulk atomic replanning, independent effort field, or automatic task management.
  An assistant can compose delegated edits; uncertain writes require readback.

The text result and structured content intentionally duplicate compatible results.
Definitions are measured as wire bytes, not claimed model-token counts. Static
concept lookup makes no task reads but still performs one native authorization
probe per HTTP request so token revocation takes effect without an identity cache.

### Bot timezone fallback

Decision: [ADR-010, 2026-11-10](../decisions/0010-semantic-api-and-mcp.md#clarification--bot-timezone-fallback-2026-11-10).

`APP_MCP_FALLBACK_TIMEZONE` is an optional deployment-wide IANA timezone. Unset or
empty disables it. Invalid values, including host-dependent `Local`, fail startup
even when MCP is disabled. No new token permissions are needed.

Resolve after a successful fresh caller profile read:

| Profile | Effective timezone | `timezoneSource` | `schedulingReady` |
| --- | --- | --- | --- |
| Any caller, populated valid timezone | Profile value | `VIKUNJA` | `true` |
| Any caller, populated invalid timezone | Profile value; never replaced | `VIKUNJA` | `false` |
| Bot (`bot_owner_id > 0`), empty timezone, configured fallback | Fallback | `BOT_FALLBACK` | `true` |
| Bot, empty timezone, no fallback | Empty | `UNAVAILABLE` | `false` |
| Ordinary user, empty timezone, with or without fallback | Empty | `UNAVAILABLE` | `false` |

`get_context.timezone` is effective timezone; additive `timezoneSource` explains
its origin. An invalid populated profile stays `VIKUNJA`; readiness independently
reports validity. Calendar-dependent tools reject unready callers with an
actionable error. Missing profile permissions remain errors, never a fallback
identity. Essential rules are in tool discovery and the permissions concept.

All MCP paths use the same resolved timezone: task detail, named lists, agenda,
recurring overview, recent/all-time activity, local mutation inputs, reminders,
completion and recurrence. Existing DST ambiguity/gap checks still apply.
Resolution only changes a request-local copy; it never writes profile settings,
changes upstream reminder behavior or affects UI/GraphQL, anonymous activity or
the Jobs HTTP integration. No caller cache or extra profile request is added.

Regression checks cover bot detection independent of username, absent fallback,
profile precedence (including matching/invalid values), ordinary-user exclusion,
denied profile reads, local midnight, both activity periods and native deadline
creation across DST. See `internal/mcp/timezone*_test.go` and
`internal/config/mcp_test.go`. Protocol fixtures verify behavior; no live bot
settings or production task writes are part of these checks.
